## Verified Independently (not trusted from any ticket's self-reported status)

- **App rename (FR-1301)**: `apps/lead-capture` exists, `apps/whatsapp-lead-capture` does not (`ls apps/`). Root `package.json` workspaces = `["apps/lead-capture", "packages/*"]`; app's own `package.json` name = `"lead-capture"`. `git log --follow -- apps/lead-capture/src/services/leadsRepo.js` returns the full 8-commit history (6 pre-rename + 2 post, back to the `5e6a262` initial commit) — history preservation genuinely holds.
- **Schema migration, on a real on-disk DB (FR-1306/1307)**: built a fresh SQLite file by hand with the OLD schema (`phone_number` column, no `channel`, no `contact_id`), inserted a row, then ran the app's real `createDb()` against that file. Confirmed: no crash, the row's `phone_number` value is now under `contact_id`, `channel = 'whatsapp'`, `phone_number` column is gone. Re-opened the same (already-migrated) file a second time — no-op, no crash (idempotency holds). Read `src/db/index.js`'s `ensureLeadsColumns()`: the `RENAME COLUMN` runs first, the `channel` `ADD COLUMN` second, and the `idx_leads_contact_id` index is created *last*, after both — this is the correct order and matches `schema.sql`'s own comment explaining why the index can't live in the static `CREATE TABLE` block (it would fail loudly against an unmigrated DB where `contact_id` doesn't exist yet). The previously-reported ordering bug is genuinely fixed.
- **`findByContact(contactId, channel)` scoping**: read the literal SQL — `'SELECT * FROM leads WHERE contact_id = ? AND channel = ? ORDER BY id DESC LIMIT 1'` (`leadsRepo.js:16-18`), genuinely scoped by both params, not a documentation claim. Wrote a throwaway script creating a WA lead and a Telegram lead with the identical `contact_id` "12345": `saveAnswers` on the WA lead did not leak into the Telegram lead's `findByContact` result — confirmed zero cross-contamination.
- **`inboundMessageProcessor.js` rename + media capture (FR-1304)**: read the file in full (589 lines). `grep phoneNumber` returns exactly one hit, inside a JSDoc comment documenting the rename itself ("TICKET-1302: renamed from `phoneNumber`") — zero actual code usages remain. `toLeadChannel()` correctly maps `whatsapp_cloud_api`/`whatsapp_baileys` → `'whatsapp'`, passes any other value (e.g. `'telegram'`) through unchanged. Traced the caption-less first-contact photo path by hand: `decideNextAction()`'s `!existingLead` branch unconditionally creates the lead regardless of text content, so the lead is created and assigned before the media-capture branch runs; the branch then appends the media note, sets `needs_review=true` via `appendAdditionalNote`, and — specifically because `hasUsableText(messageBody)` is false — resets `replies` to `[]`, overriding whatever `START_FLOW` had queued (ack+Q1). The full suite's TICKET-1305 tests exercise exactly this path and pass. Confirmed separately that a photo WITH a caption skips the `replies = []` reset entirely, leaving the normal product-matching flow (Q2 sent, `matched_product` updated) untouched — the media note is purely additive in that case.
- **`@rimba/telegram-connector` (FR-1303)**: read `telegramConnector.js` in full. Grepped every `log(` call site — all pass either a static endpoint-name string (`'telegram_get_updates_failed'`, `'telegram_send_message_failed'`, etc.) or token-free details (`status`, `error.message`); the token-embedding `baseUrl` string is never passed to `log()`. Malformed-update handling: `normalizeUpdate()` throws on a genuinely malformed shape (e.g. missing `chat.id`), and `processUpdate()` catches that throw, logs `telegram_malformed_update`, and returns — confirmed this never escapes `pollOnce()`'s per-update loop. **`stop()` hang bug**: wrote a throwaway test that starts the connector with a 60-second `pollIntervalMs` (so the poll loop is genuinely parked in a long `sleep`), then calls `stop()` and races it against a 3-second timeout — `stop()` resolved in ~0ms. Read why: `stop()` only flips the `polling` flag and nulls `pollChain`, deliberately never awaiting the in-flight `sleep()` promise — the fix is real, not just claimed.
- **`server.js` composition-root wiring (FR-1302)**: read `createTelegramChannel()` in full — `const token = (telegramBotToken || '').trim(); if (!token) return null;` gates construction of the leadsRepo/settingsRepo/processor/connector entirely; confirmed via the test suite's own unset/blank-token test and by inspection that nothing is constructed in that branch. `markAsRead` is confirmed omitted from the Telegram processor's `createInboundMessageProcessor({...})` call (`server.js:161-172` has no `markAsRead` key) — genuinely relies on the processor's existing optional-defaults-to-no-op behavior, no new code path. Diffed `server.js` against its pre-feature state (commit `59b0caf`): every line touched is a pure addition (new function, new call sites, new log fields, new `if (telegramChannel)` blocks) plus one structural change — `main()` is now called only under `require.main === module` and exported, rather than called unconditionally at module load — needed to make `createTelegramChannel` testable without booting a real server; this does not change runtime behavior when the file is run as the entrypoint (same as before). Every WA-specific line (`WHATSAPP_MODE` sub-switch, Cloud API / Baileys construction, `assertRequiredEnv`) is byte-for-byte unchanged.
- **Dashboard (FR-1305/1306)**: `listAllMostRecentFirst({ channel } = {})` — read the code: when `channel` is falsy it calls the literal pre-existing `listAll` prepared-statement object (`listAll.all()`), not a rebuilt/dynamic query — confirmed the no-filter path is genuinely untouched. The route (`leads.js`) validates `req.query.channel` against `['whatsapp','telegram']` before use, defaulting anything else to `''` (all channels), and persists the selection into the rendered `<select>`. `leads.ejs` defines `.badge-channel-whatsapp`/`.badge-channel-telegram` CSS and applies them via `badge-channel-<%= lead.channel %>` per row — correctly interpolated, and the header reads "Contact" (not "Phone number") per `ux.md`.
- **Full regression**: `npx turbo run test --force` (not cached) — 5/5 tasks pass. `@rimba/humanized-timing` 10, `@rimba/telegram-connector` 10, `@rimba/whatsapp-connector` 44, `@rimba/product-matcher` 35, `lead-capture` 211. **Total 310, 0 failing, 0 skipped, 0 todo.**
- **Cross-cutting**: `TELEGRAM_BOT_TOKEN` is absent from both `BASE_REQUIRED_ENV_VARS` and `CLOUD_API_REQUIRED_ENV_VARS` in `server.js` — confirmed boot never requires it. `.env.example` documents it as optional/commented-out with a clear "leave unset to run WhatsApp-only" note. `scripts/extract-app.js`'s `resolveAppDir(appName)` takes the app name as a runtime argument with no hardcoded old path anywhere in the script (confirmed by full read); ran a real extraction against `lead-capture` and confirmed `.env` is excluded, only the secret-free `.env.example` template survives, and `@rimba/telegram-connector` is correctly vendored alongside the other three packages.

## Blind Spots
- Did not independently re-derive every one of the 310 tests' assertions line-by-line — spot-checked the TICKET-1304/1305/1306-specific tests (Telegram wiring, media capture, dashboard filter) directly against the code, and trusted the pre-existing WA suite's pass/fail count as the regression signal for "untouched" claims, consistent with how the 001 review handled the same scale of pre-existing coverage.
- Did not fuzz `normalizeUpdate()` against arbitrary malformed JSON shapes beyond the one hand-constructed case (missing `chat.id`) plus what the package's own test suite covers — plausible that some other malformed shape could throw a *different* kind of error not caught by the same try/catch, though the catch in `processUpdate()` wraps `normalizeUpdate()` unconditionally, so structurally any thrown error (not just the one tested) is caught.
- Did not test behavior under real concurrent load (simultaneous WA + Telegram messages under real I/O timing) — the "no cross-talk" claim is verified at the unit/integration level (two synthetic contacts through two processor instances), not under a real race condition.

## Verdict: **PASS**

## Confidence: High

The feature achieves its stated goal: Telegram is genuinely a second concurrent channel sharing the same lead/product/state-machine logic as WhatsApp, with zero behavioral change to WA when `TELEGRAM_BOT_TOKEN` is unset (verified by diff, not just by test pass/fail counts). Both previously-reported bugs this review was specifically asked to re-check — the migration/index ordering bug and the `stop()` hang — are genuinely fixed, confirmed by targeted reproduction rather than by trusting the ticket files' claims. The one loose end (stale README paths) was closed as part of this review; the one remaining cosmetic issue (stale package-lock name) is flagged for a human to clean up but blocks nothing.
